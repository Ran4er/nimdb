# ADR-001: Движок базы данных на Nim

**Статус:** accepted  
**Дата:** 2025-01  
**Авторы:** NimDB core team

---

## Контекст

Нам нужен язык для реализации низкоуровневого storage-движка:
управление страницами памяти (8 KB), WAL с побайтовой точностью,
buffer pool с LRU-eviction, SIMD-векторные вычисления, MVCC-версионирование.

Требования:
- ручное управление памятью (или минимальный GC без пауз)
- доступ к низкоуровневым C-примитивам (`copyMem`, `addr`, `cast`)
- компиляция в нативный бинарник без рантайм-зависимостей
- продуктивность написания кода уровня C, но с нормальным синтаксисом
- возможность генерировать C-заголовки для FFI (Go cgo, Python ctypes, JNI)

---

## Рассмотренные альтернативы

### C / C++
**За:** максимальная производительность, зрелая экосистема, прямой AVX-доступ.  
**Против:** высокий когнитивный overhead (UB, manual memory, отсутствие
нормальной системы модулей). Для демонстрационного проекта время написания
важно — на C движок аналогичного масштаба занял бы 3–4× дольше.  
**Решение:** C/C++ выделен в отдельный модуль `drivers/c/` для SIMD-библиотеки
(AVX2/AVX-512), где контроль над intrinsics критически важен.

### Rust
**За:** memory safety без GC, отличная производительность, `unsafe` для
низкоуровневого кода.  
**Против:** steep learning curve ownership/borrow checker замедляет итерации
на этапе проектирования архитектуры хранилища; async-экосистема сложнее
для однопоточного event loop storage-движка.  
**Итог:** Rust был бы хорошим выбором для production-системы, но снижает
скорость прототипирования, что критично на этапе proof-of-concept.

### Go
**За:** простота, отличный tooling, GC с очень короткими паузами (< 1 ms).  
**Против:** GC — принципиальная проблема для storage-движка: мы сами
управляем пулом страниц (buffer pool), GC поверх этого создаёт непредсказуемые
паузы; нет `union`-типов; нет низкоуровневых SIMD-примитивов.  
**Решение:** Go — идеальный выбор для gateway и CLI, а не для движка.

### Java / JVM
**Против:** JVM overhead, GC, невозможность явно управлять page-aligned
аллокациями без `Unsafe`/`ByteBuffer` хаков. JVM — правильный выбор
для JDBC-драйвера и сервисного слоя, не для движка.

---

## Принятое решение: Nim

Nim компилируется в C (который затем собирается gcc/clang), что даёт:

- **Производительность:** идентична C при `-d:danger -O3 -march=native`
- **Низкий уровень:** `addr`, `cast[T]`, `ptr UncheckedArray[T]`, `copyMem`
  без боли — прямой доступ к памяти страниц как `array[8192, byte]`
- **C FFI:** `{.exportc.}` генерирует C-совместимый ABI; заголовки для
  Python/Go/Java пишутся один раз
- **Metaprogramming:** макросы и templates для генерации сериализации
  протокола без boilerplate
- **Нет GC-пауз в критических путях:** Nim поддерживает `--mm:arc`
  (ARC — deterministic reference counting без stop-the-world) — именно то,
  что нужно для storage-движка с предсказуемой latency
- **Модули:** нормальная система пространств имён, в отличие от C

### Конкретные применения в движке

| Компонент | Почему Nim выигрывает |
|-----------|-----------------------|
| Page layout | `cast[ptr PageHeader]` на raw `array[8192,byte]` — zero-cost абстракция |
| WAL | `--mm:arc` гарантирует отсутствие GC-пауз при sequential write |
| Buffer pool Clock eviction | Tight loop без аллокаций — компилируется в 5–10 инструкций |
| SIMD dot product | 4-way unroll → auto-vectorization LLVM/GCC в AVX2 |
| HNSW insert | Ptr-арифметика без overhead умных указателей |

## Последствия

**Положительные:**
- Бинарник без рантайм-зависимостей — `nimdb` запускается как единый
  исполняемый файл, `nimdbctl start` не тянет JVM/Python
- C FFI позволяет Python/Java/Go использовать движок через `libnimdb.so`
  без переписывания
- Производительность SIMD-вычислений сопоставима с C при значительно
  меньшем объёме кода

**Отрицательные / риски:**
- Nim — нишевый язык; hiring pool ограничен. Для NimDB это осознанный
  trade-off: это исследовательский/portfolio-проект, не production-продукт
  с командой разработчиков.
- Debugging сложнее, чем в Go/Rust: gdb/lldb работают, но IDE-поддержка
  слабее. Решение: добавить логирование WAL-replay для диагностики.

---

## Метрики успеха

- dot product на 1M элементов: цель ≥ 3 GFLOPs (vs ~1.8 у наивного C-цикла)
- WAL write latency p99: < 0.5 ms (при синхронном flush на NVMe)
- Buffer pool hit rate: > 95% для рабочего набора данных, помещающегося в 16 MB
