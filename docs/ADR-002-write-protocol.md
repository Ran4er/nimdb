# ADR-002: Бинарный wire-протокол NDP (NimDB Data Protocol)

**Статус:** accepted  
**Дата:** 2025-01

---

## Контекст

NimDB должна поддерживать клиентов на Go, Java, Python, C. Нам нужен
единый протокол коммуникации между клиентом и движком, который:

- однозначно парсится (нет ambiguity в границах сообщений)
- поддерживает мультиплексирование (несколько запросов по одному TCP-соединению)
- эффективно передаёт большие результаты (OLAP-сканы могут быть GB)
- достаточно прост для реализации за разумное время на 4 языках
- имеет тестируемую спецификацию (test vectors)

---

## Рассмотренные альтернативы

### Текстовый line-protocol (Redis-inline)
**За:** прост в реализации, удобен для отладки через `nc`/`telnet`.  
**Против:** нет бинарных данных (вектора, Arrow-чанки), нет мультиплексирования,
парсинг медленный для больших result set'ов.  
**Решение:** оставить как REPL-режим для `nimdbctl shell`, но не как основной протокол.

### PostgreSQL wire protocol (Frontend/Backend)
**За:** стандарт де-факто, JDBC/psycopg2 уже умеют.  
**Против:** сложная machine state (много типов сообщений, аутентификация,
Extended Query Protocol). Реализовать корректный PG-wire на Nim — проект
внутри проекта; нарушает цель "показать свой дизайн протокола".  
**Итог:** можно добавить PG-wire compatibility как опциональный proxy-слой
поверх NDP — тогда DBeaver заработает без нового драйвера.

### gRPC + protobuf
**За:** автогенерация клиентского кода на всех языках, streaming, TLS из коробки.  
**Против:** зависимость от protobuf runtime на каждом клиенте;
сложно для мобильного C-клиента; сложнее объяснить "как это работает
внутри" на собеседовании, чем собственный бинарный протокол.  
**Итог:** gRPC используется в Go-gateway как внешний интерфейс (между
Go-gateway и внешними сервисами), но не между клиентскими драйверами
и Nim-движком.

### Apache Arrow Flight
**За:** нативная поддержка Arrow-чанков, высокая пропускная способность.  
**Против:** протокол заточен под batch-передачу данных, не под OLTP-запросы;
overhead gRPC-рантайма.  
**Итог:** Arrow Flight рассматривается как оптимизация для bulk-export
(OLAP + ML pipeline) в будущем, но не как основной протокол.

---

## Принятое решение: NDP — собственный бинарный протокол

### Обоснование

Собственный протокол даёт:
1. Полный контроль над форматом для поддержки специфических типов NimDB
   (VECTOR, GraphQuery, ModelOp)
2. Возможность показать глубокое понимание протокольного дизайна
3. Простота реализации на уровне C — важно для нативного клиента

### Ключевые принципы дизайна

**Фреймирование:** каждое сообщение имеет фиксированный заголовок фиксированного
размера → нет ambiguity в парсинге, не нужен разделитель строк.

**Мультиплексирование через RequestId:** клиент может отправить несколько
запросов не дожидаясь ответа на предыдущий (pipelining). Ответы могут
прийти не по порядку — клиент сопоставляет по `requestId`.

**Streaming result:** большой result set разбивается на DATA_CHUNK-сообщения.
Каждый чанк — готов к передаче в Arrow или в memory напрямую. Это ключевое
для ML-pipeline (выгрузка эмбеддингов в Python без промежуточного буфера).

**Расширяемость:** поле `flags` в заголовке и зарезервированные opcode-диапазоны
позволяют добавлять новые операции без версионного разрыва.

## Последствия

**Положительные:**
- Полный контроль над форматом данных, особенно для Arrow-chunk payload
- Тонкий runtime: клиент = TCP socket + 200 строк парсера фреймов
- Чёткий тестируемый контракт: byte-точные test vectors в `protocol/`

**Отрицательные:**
- Нет автогенерации клиентского кода (в отличие от gRPC) — каждый
  драйвер пишется вручную. Это осознанный выбор: цель — показать
  умение реализовывать протокол, а не использовать генераторы.
- DBeaver/TablePlus не подключатся "из коробки" — нужен отдельный
  PG-wire proxy или JDBC-драйвер. JDBC-драйвер на Java закрывает это.
